这是一周本机 Grok CLI 使用记录的复盘。问题并不是“我到底发出了多少句话”，而是一次 Agent 循环会把当时的整窗上下文再次送进模型。只看输出，容易低估实际输入；只看“未缓存”，又会把缓存命中之外的那一小段误认为全部输入。本文把实测、已知下限、均值补全和按产品百分比反推严格分开。

> **资料口径**：本文使用的快照生成于 2026-08-30，周期为本机 UTC+13 的 2026-08-23 08:43 至 2026-08-30 08:43。文中的价格、模型名称和产品百分比都是该快照的记录，不代表之后仍然不变。

## 先说口径与局限

本周产品界面显示使用了周限额的 22%，但本机 `unified.jsonl` 并没有保存完整一周的逐次 token。它只保留了周期最后约十小时的 `shell.turn.inference_done` 记录：这部分一共 879 次推理、1.46 亿输入 token，是**有账部分的实测下限**，不是完整周账。

磁盘上的 session `events.jsonl` 能覆盖整周的循环、工具和 turn 数，但缺少逐次 token。因此，下面会同时出现四种数字：日志直接读出的实测值、从它得到的下限、按已记录循环均值补全的估算，以及把实测值除以 22% 得到的情景反推。它们回答的是不同问题，不能互相冒充。

## 一眼看懂：22% 到底意味着什么

本周有 tokenizer 账的部分，模型一共吃进去 <text-mark tone="thesis" effect="pill">145,551,079</text-mark> 个输入 token，吐出 <text-mark tone="thesis" effect="pill">892,684</text-mark> 个输出 token，合计约 <text-mark tone="thesis" effect="pill">146,443,763</text-mark> 个 token。产品界面显示这相当于本周限额的 <text-mark tone="warn" effect="pill">22%</text-mark>。

如果暂时接受“这部分就是 22%”这个反推假设，那么：

| 口径 | 数值 | 如何得到 |
|---|---:|---|
| 已记录使用量 | 约 1.46 亿 token | prompt + completion |
| 以 22% 反推的一周满额 | 约 6.66 亿 token | 已记录量 ÷ 0.22 |
| 以四周计的一月满额 | 约 26.6 亿 token | 一周反推 × 4 |
| 按已记录循环均值补全的一周原始量 | 约 14.02 亿 token | 879 次有账 + 973 次缺口估算 |

这里的 `6.66 亿` 和 `26.6 亿` 不是“我本周真正用满了这么多”，而是把产品显示的 22% 当作线性刻度后的情景数字。更早的 973 次循环没有逐次 token，不能用一个看似精确的除法把它们变成事实。

<inset-card id="weekly-lower-bound" eyebrow="01" kicker="KNOWN LOWER BOUND" title="先把数字放回它能证明的范围">
已记录的 1.46 亿 token 可以证明“至少有这么多输入和输出被记账”。它不能证明整周只有这么多，也不能单独证明产品的完整额度。读周账时，先看测量窗口，再看数字大小。
</inset-card>

## 先把一个误会拿掉：未缓存不是总输入

上一版总览把“未缓存输入 823 万”和“输出 89 万”摆在最显眼的位置，这个重点是错的。官方字段语义里，每次循环的 `prompt_tokens` 才是送进模型的输入；`cached_prompt_tokens` 是输入中命中缓存的部分；未缓存输入只是两者相减：

$$
\text{uncached\_prompt} = \text{prompt} - \text{cached\_prompt}
$$

Agent 每调用一次工具，都可能把当时的整窗再次送进去。所以一场长对话累计几千万输入并不奇怪。最大的一场对话名为 `Catalog cleanup, SOP, and restored shelf bugs`，它自己就有约 **7,513 万输入 token**，对应 545 次有账循环；823 万只是全周输入里没有命中缓存、需要新计算的那一段。

<aside-note id="uncached-warning" kind="warn" title="823 万不是这一周的总输入">
本周总输入是 145,551,079；其中缓存输入 137,322,112，未缓存输入 8,228,967。把未缓存部分当成“总输入”，会把 Agent 的上下文重复成本缩小一个数量级以上。
</aside-note>

| 对照项 | 数值 | 含义 |
|---|---:|---|
| 最大一场对话的累计输入 | 约 7,513 万 | 545 次有账循环累计送入 |
| 本周全部有账循环的累计输入 | 约 1.46 亿 | 879 次有账循环合计 |
| 其中未缓存输入 | 约 823 万 | 输入中需要新计算的部分 |
| 本周全部输出 | 约 89 万 | 含思考输出与可见输出 |

## 缓存是怎么算的，输入输出比为什么这么夸张

缓存命中率按每次 `inference_done` 的缓存 prompt 除以 prompt，再在全周求和：

$$
\text{缓存命中率} = \frac{137{,}322{,}112}{145{,}551{,}079} \approx 94.35\%
$$

输入与输出的比例约为：

$$
\text{输入:输出} = \frac{145{,}551{,}079}{892{,}684} \approx 163:1
$$

也就是说，每让模型新写出 1 个 token，平均同时又把约 <text-mark tone="thesis" effect="pill">163</text-mark> 个旧 token 送进去。其中约 154 个走了缓存价格，约 9 个属于需要重新计算的输入。这正是工具循环和长上下文共同造成的结果：模型的“回答字数”并不等于模型处理过的“上下文长度”。

| 指标 | 结果 | 解释 |
|---|---:|---|
| 缓存命中率 | 94.35% | 137,322,112 ÷ 145,551,079 |
| 累计输入 : 累计输出 | 163 : 1 | 145,551,079 ÷ 892,684 |
| 未缓存输入 : 输出 | 约 9.2 : 1 | 8,228,967 ÷ 892,684 |
| 有账长上下文循环 | 300 / 879 | 单次输入达到 200k 的循环 |

每次有账循环平均送入约 **165,587 个输入 token**，输出约 **1,016 个 token**；其中输出的约 84% 是思考部分。输出很短，并不代表这一轮上下文很短。

<timeline-block id="billing-data-chain" title="这份周账是怎样拼出来的">
- **统一日志** — 从 `shell.turn.inference_done` 读取逐次 prompt、缓存、未缓存、completion 和价格字段。
- **879 次有账推理** — 这些记录位于本周周期内，构成可直接测量的 token 下限。
- **session 事件** — 从各 session 的 `events.jsonl` 得到全周 1,852 次模型循环，但其中 973 次没有逐次 token 字段。
- **均值补全** — 用已记录循环的平均输入、缓存和输出估计缺失部分，只用于展示区间，不冒充日志。
- **产品 22%** — 这是界面上的使用百分比，不能反向证明 xAI 的实际计量公式。
</timeline-block>

## 缓存命中不等于“没有成本”

缓存命中降低了新计算的输入成本，但缓存部分仍然属于模型接收的上下文，也仍然占用窗口和带宽。把缓存 token 从总输入里删掉，只能回答“有多少输入需要新算”，不能回答“模型一共看了多少内容”。

以后粗略估算用量，可以先记住这组本机样本比例：典型循环约送入 16.6 万、吐出 1,000；缓存维持在九成四左右时，新算输入约占总输入的 5.7%。如果 Agent 循环数量继续增加，输入会近似随循环数线性增长，而输出增长得慢得多。

这不是一个适用于所有模型和所有任务的定律。它只是本周这份日志的形状，真正做预算时仍应按自己的上下文大小、缓存策略和长上下文档位重新测量。

## 换算成 API 大概多少钱

原 HTML 按快照记录的 Grok-4.6 价格计算：短上下文输入 `$2` / 百万 token，缓存输入 `$0.50` / 百万 token，输出 `$6` / 百万 token；单次输入达到 200k 时按长上下文价格，即输入 `$4`、缓存 `$1`、输出 `$12` / 百万 token。这里的价格是生成日的记录，应当与订阅产品的周限额分开理解。

xAI 并没有在这份材料里公布 Grok CLI / SuperGrok Heavy 的周 token 计量规则。`÷ 0.22` 只是把产品界面百分比当作线性刻度的情景推演；API 标价也不等于订阅产品实际扣款。价格、模型和长上下文规则发生变化时，这一节需要重新计算。

## 879 次有账推理：长上下文档位会改变价格

本周 <text-mark tone="thesis" effect="pill">879</text-mark> 次有账推理中，有 <text-mark tone="thesis" effect="pill">300</text-mark> 次输入达到或超过 200k，579 次低于 200k。达到阈值后，原稿按整单价格翻倍计算，因此不能只把总 token 乘一个平均单价。

| 推理档位 | 次数 | 占有账推理 | 影响 |
|---|---:|---:|---|
| 不到 200k | 579 | 65.9% | 短上下文价格 |
| 达到或超过 200k | 300 | 34.1% | 原稿按长上下文整单翻倍 |
| 合计 | 879 | 100% | 每次工具循环独立计价 |

原始 HTML 提供两个筛选器：按 session id 查某个会话的循环，按 `short` / `long` 观察上下文档位。这里保留它们作为交互明细，而不是在 Markdown 中再实现一个静态版筛选器。

## 从这周账本得到的几个动作

这份数据最值得留下的不是某个美元数字，而是上下文形状带来的工程提醒：

1. **长会话要主动拆分。** 每一次工具循环都可能重复携带整窗，历史越长，下一次循环的输入越大。
2. **缓存要保持连续。** 缓存命中率达到 94% 并不等于没有输入成本，但它显著改变了新计算部分的价格。
3. **长上下文单独观察。** 200k 阈值会改变整单价格，平均单价会掩盖这部分影响。
4. **把“实测、下限、估算、反推”分栏记录。** 这样下一次日志窗口变化时，不会把不同口径拼成一个假精确数字。
5. **把交互明细和结论分开。** 搜索 42 场会话、查看 879 次循环适合交互 HTML；文章正文更适合解释这些数字怎样产生。

这一周真正能从日志证明的是：在约十小时的有账窗口里，879 次推理累计送入约 1.46 亿 token，其中 94.35% 命中缓存，输出约 89 万 token。其余整周规模只能通过明确写出的假设去估算，不能把 22% 反推当成官方额度。
</inset-card>

这篇周账本不会自动更新。下一周如果要继续记录，应生成新的快照、重新标注周期边界，并把新的 `data.js` 与本文的旧版本分开；不要悄悄覆盖这篇文章的历史数据。
