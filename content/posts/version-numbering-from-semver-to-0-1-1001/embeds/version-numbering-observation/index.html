术语正名：每一位的官方名称

THESIS版本号三段式的官方名称是 major / minor / patch，第三位也叫 micro——你观察到的「1.x 或 2.1.1000 多」里那个不停增长的数字，就是第三位（修订号）。

在讨论任何规则之前，先给每一位一个名字。版本号不是「一堆点分数字」，每一段都有官方术语、有分工、有归谁管的规矩。

图 1.1 — 版本号 2.1.1001-rc.1+20260830 的结构解剖

三段式：MAJOR.MINOR.PATCH§1.1

语义化版本规范（Semantic Versioning 2.0.0，semver.org）对三段式的官方定义如下表。「递增条件」一栏是规范原文，后文章节会反复回到这三句话。

位官方术语中文递增条件（官方原文）
第一位major version主版本号“when you make incompatible API changes”（不兼容的 API 修改）
第二位minor version次版本号“when you add functionality in a backward compatible manner”（向下兼容的功能新增）
第三位patch version修订号“when you make backward compatible bug fixes”（向下兼容的问题修正）

第三位的别名：micro§1.2

「第三位」在不同体系里有不同的官方名字，指的都是同一个位置：SemVer 官方叫 patch；Python 官方 sys.version_info 元组定义为 (major, minor, micro, releaselevel, serial)——第三位叫 micro；CalVer（日历版本，见第六章）官方规范同样使用 micro；口语中也叫 maintenance version（维护版本）。

这个术语辨析不是咬文嚼字：patch 暗含「修复缺陷」的语义，而 micro 只是「最小位」。如果一个项目的第三位承载的是「每一次发布，不管内容是什么」，micro 是更准确的叫法。

第四位：build / revision§1.3

SemVer 没有第四位，它出现在另外两个体系里：

  • 微软 .NET 四段式：major.minor.build.revision，如 Windows 内部版本 10.0.19045.4046。早期 .NET 甚至推荐 major.minor.* 通配符——编译器自动把 build 设为「自 2000-01-01 起的天数」、revision 设为「当天秒数的一半」，第四位本质是时间戳。
  • 支付宝四段式：如 12.12.20.8000（2026-08 官网在架版本），第四段承载高频构建号。

先行版与构建元数据§1.4

SemVer 在 X.Y.Z 之后还允许两种修饰，语法严格：

  • 先行版本号（pre-release）：连字符 - 后接点分标识符，如 1.0.0-alpha、1.0.0-rc.1。先行版优先级低于对应正式版，官方完整排序链为：1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-alpha.beta < 1.0.0-beta < 1.0.0-beta.2 < 1.0.0-beta.11 < 1.0.0-rc.1 < 1.0.0
  • 构建元数据（build metadata）：加号 + 后接点分标识符，如 1.0.0+20130313144700。比较版本时必须忽略——仅构建元数据不同的两个版本优先级相同。
本章结论 · §1 SUMMARY

日常所说的「版本号第几位」，官方叫法为：第一位 major（主版本号）、第二位 minor（次版本号）、第三位 patch / micro（修订号）、第四位 build / revision（构建号）。「1.x 或 2.1.1000 多」的形态 = 冻结第一、二位，让第三位（micro）无限递增。

SemVer：约定俗成的「官方答案」

THESISSemVer 是业界唯一被广泛书写的版本号规范，但它的适用对象是「有公共 API 的库」，而不是所有软件；它对 0.y.z 阶段的官方定义，恰好为「只在低位递增」提供了规范内依据。

起源：为「依赖地狱」而生§2.1

SemVer 由 Gravatar 创办者、GitHub 联合创始人 Tom Preston-Werner 建立，要解决的问题是依赖地狱（dependency hell）：包管理器需要知道「升级到 1.3.0 会不会弄坏我的项目」，因此版本号必须承载兼容性语义。规范关键词 MUST / SHOULD / MAY 按 RFC 2119 解读，共 11 条规则，核心四条：

  • 软件必须声明公共 API（规则 1）；
  • 版本号必须是 X.Y.Z 格式：非负整数、禁止前导零、逐位数值递增（规则 2）；
  • 已发布的版本内容不可修改，任何修改必须以新版本发布（规则 3）；
  • 递增规则：PATCH ← 向下兼容的修复；MINOR ← 向下兼容的新功能（递增时 PATCH 归零）；MAJOR ← 任何不兼容改动（递增时 MINOR、PATCH 归零）（规则 6/7/8）。
图 2.1 — SemVer 递增决策：改动类型 → 升哪一位 → 谁归零

0.y.z：官方的「初始开发阶段」§2.2

规范第 4 条对 0.x 给出了明文定义——这是全书最重要的一段引文：

"Major version zero (0.y.z) is for initial development. Anything MAY change at any time. The public API SHOULD NOT be considered stable." 主版本号为零（0.y.z）的软件处于开发初始阶段，一切都可能随时被改变。这样的公共 API 不应该被视为稳定版。 — Semantic Versioning 2.0.0, spec item 4（semver.org）

也就是说，0.x 是一张制度化的免责声明。官方 FAQ 进一步明确（以下均为官方问答的直译）：

  • 0.x 阶段怎么递增？「最简单的做法是以 0.1.0 作为初始化开发版本，并在后续每次发行时递增次版本号。」
  • 什么时候该发 1.0.0？三个信号：「软件被用于正式环境；已有稳定 API 被使用者依赖；开始很担心向下兼容。」
  • 0.x 阻碍快速迭代吗？「主版本号为零的时候就是为了做快速开发。如果你每天都在改变 API，你应该仍在 0.y.z 阶段。」
  • 小改动就升 MAJOR，岂不是很快到 42.0.0？官方回答：「这是开发的责任感和前瞻性的问题。不兼容的改变不应该轻易被加入到有许多依赖代码的软件中……要递增主版本号意味着你必须为这些改变的影响深思熟虑。」

采用情况：库的生态事实标准§2.3

生态 / 项目状态关键事实
npm（JavaScript）官方推荐建议包从 1.0.0 起步；^1.0.4 兼容次版本、~1.0.4 仅修订
Cargo / crates.io（Rust）事实标准dtolnay/semver 为官方解析器；Cargo 文档专设 SemVer 兼容性章节
Go Modules官方强制v2+ 主版本号进入模块路径：example.com/m/v2
Kubernetes官方采用「x.y.z, following Semantic Versioning terminology」
React自 15.0.0 采用2016 年从 0.14.7 直接跳 15.0.0：「我们只是把 0 从开头挪到了结尾」
Angular自 2.0 采用但按日历节奏发主版本——语义让位排期（见第四章）
本章结论 · §2 SUMMARY

SemVer 是写给库作者的契约：版本号 = 兼容性承诺。它自洽且被广泛接受，但有两个前提——①假设存在清晰的「公共 API」；②递增规则只在「有人依赖你的接口」时才有意义。对一个独立应用（没有被别人 import 的 API），SemVer 的约束天然减弱——这正是后面各章各种「不规矩」实践的规范缝隙。

冻结高位：知名软件的「1.x 长跑」

THESIS大量顶级软件把第一、二位冻结数年甚至数十年，让第三位（或更低位）承载全部日常迭代——「1.x 长跑」不是不专业，而是主流实践。

这一章直接回答疑问 (b)。你观察到的现象普遍存在，而且每一个案例背后都有深思熟虑的理由。

五个标本§3.1

微信：8.0.x，第一位五年七个月未动。微信 8.0（iOS）发布于 2021 年 1 月 21 日——微信十周年当天，此前最高版本 7.0.22。此后至 2026 年 8 月，版本号一直在 8.0.x 序列滚动。主版本号在微信手里是纯粹的「营销叙事工具」：十周年、大改版才 +1；日常功能更新全部压进第三位。

macOS：10.x 用了十九年。2001 年 Mac OS X 10.0 发布，此后 15 个大版本（10.0 → 10.15，2019）全部以「10.x」命名——「10」（罗马数字 X）实质是品牌，真正的代际在第二位。2020 年 Big Sur 跳到 11 时，甚至要保留一个 SYSTEM_VERSION_COMPAT 机制对旧软件自报 10.16，以兼容写死检查「10.x」字符串的程序。

Minecraft：1.x 十五年，社区默认永远没有 2.0。正式版 1.0 发布于 2011 年 11 月；2024 年发布 1.21「棘巧试炼」，2026 年仍在 1.21.x 序列。1.13「扁平化」、1.16 下界更新、1.18 洞穴与山崖都是伤筋动骨的大更新，却只是「1.x」——第二位早已承担主版本职能。庞大的模组生态深度绑定具体 1.x.y，是「永不 2.0」的现实约束。

Microsoft Office：内部版本号冻结在 16.0 的十一年。序列：2003 = 11.0 → 2007 = 12.0 → 2010 = 14.0（跳过 13，避讳）→ 2013 = 15.0 → 2016 = 16.0——此后冻结至今。Microsoft Learn 官方文档原话：「Microsoft 365、Office LTSC 2024/2021、Office 2021/2019/2016 共用相同的版本号码：16.0。」冻结原因：转向订阅制后对外区分靠品牌名与 YYMM 月度 build 号；内部主版本号被钉死以保住 VBA、COM 加载项、注册表路径兼容性——安装目录至今叫 Office16。

OpenSSL：0.9.x 十二年，字母表当补丁位。1998–2010 年一直是 0.9.x（0.9.8 系列发了十几年），2010 年才发布 1.0.0。此后补丁版本用字母：1.0.2a 一路排到 1.0.2u，1.1.1 一路排到 1.1.1w——「1.1.1」这个版本号延续十余年，内部实际历经 23 个字母补丁。2018 年宣布弃用该方案，新版本线从 1.1.1 直接跳到 3.0.0（2021）。

图 3.1 — 「高位冻结」年限：同一个主版本号活了多久（截至 2026-08）

更多长跑者§3.2

  • React Native：至今仍是 0.x（2026 年最新 0.87.x），Meta 明确表示暂无 1.0 计划——全球使用最广泛的 ZeroVer 项目；
  • three.js：至今 0.x（如 0.171.0），每 6 周升一次 minor，minor 实际承担破坏性变更角色；
  • 手机 QQ：8.0（2019-04）→ 9.0（2023-12），四年憋一次主版本；9.0 的由头是 QQNT 跨平台架构换代——技术代际才配动第一位。
本章结论 · §3 SUMMARY

高位数字冻结的原因各不相同：营销叙事（微信）、品牌惯性（macOS）、生态绑定（Minecraft）、兼容性自保（Office）、治理保守（OpenSSL）。但结果相同：版本号的高位变成「叙事权」，低位变成「节奏权」。疑问 (b) 得到系统性证实。

通胀派：当版本号变成日历

THESIS与「冻结高位」相对的另一个极端是「主版本号通货膨胀」——Chrome 十八年滚出 152 个主版本，主版本号彻底退化为时间刻度；业界称之为 major version inflation。

Chrome：每年 +8 的版本号通胀§4.1

Chrome 2008 年 9 月发布，2026 年 8 月稳定版为 Chrome 152——18 年 152 个主版本，年均约 +8.4。节奏演进：早期 6 周一版 → 2021 年起 4 周一版 → 官方宣布 2026 年 9 月起（Chrome 153 起）改为每两周一版。主版本号彻底沦为计数器：用户无感（浏览器自动更新），真正的版本信息在四段 build 号（如 152.0.7977.65）与 release note 里。这就是「evergreen browser」哲学。

图 4.1 — 主版本号通胀：Chrome / Firefox 的主版本号-年份曲线（约 18 年 150 个主版本）

v100 危机：通胀引发的迷你 Y2K§4.2

2022 年 Chrome 与 Firefox 双双逼近第 100 版时，大量网站的 UA 解析库按两位数主版本硬编码，Chrome/100 会被错解析为 Chrome/10 而拒绝服务。Mozilla 与 Google 为此做了 UA 冻结实验与版本 100 兼容测试，后备方案竟是把主版本号冻结在 99、或对特定站点谎报版本——版本号通胀反噬工程的标志性事件。

跟随者与排期制§4.3

  • Firefox：1.0（2004）到 4.0 用了约 6 年；2011 年宣布转向快速发布，从 4.0 到 5.0 仅 3 个月。学术研究明确指出此举「部分是为与 Chrome 的快速发布竞争」。2020 年起 4 周一版，2026 年已在 148+ 序列；企业侧另有每年一个大版本的 ESR 通道。
  • Angular：官方采用 SemVer，但按日历节奏发主版本——v22 之前每 6 个月一个大版本，之后每 12 个月一个。主版本号实际成为「时间刻度」，与「是否有破坏性变更」脱钩。

Linux 内核：「手指和脚趾」规则§4.4

Linux 内核的版本演变是「数字管理压倒语义」的最佳标本。2.6 系列用了 8 年（停在 2.6.39）；此后每次跳主版本，Linus 给出的理由都与技术无关：

跳变年份Linus 本人的理由（有原话可考）
2.6.39 → 3.02011内核 20 周年 +「2.6.39 的 .39 太长了」——明确说 3.0 没有任何技术里程碑意义
3.19 → 4.02015「3.x 数到 19，我的手指和脚趾都数不过来了（I'm running out of fingers and toes）」
4.20 → 5.02019「4.x 数到 20 又数不过来了」，明确说 5.0「不意味着任何特殊变化」
5.19 → 6.02022同样逻辑
6.x → 7.02026-04同样的「手指脚趾」规则再度生效

自 3.0 起，内核 major 位 = 「minor 快数到 20 了」的计数器；真正的兼容性承诺只有一条「不破坏用户空间」，与版本号完全解耦。

其他通胀样本§4.5

  • 抖音：2016 年 9 月从 1.0 起步，2026 年 8 月已是 40.2.0——主版本号只反映迭代节奏；
  • systemd：原本 0–44 正常递增，2012 年因合并 udev（其独立时代最后版本是 182）直接跳到 183，宣布以后每次发布只 +1，2024 年已到 256；
  • 支付宝：主版本号已悄悄走到 12.x（且是四段式 12.12.20.8000）。
本章结论 · §4 SUMMARY

通胀与冻结看似相反，本质同源：一旦主版本号不再承诺「重大性」，涨或不动只是习惯。回答疑问 (a)：「每次更新必升大版本」在业界只存在于 Chrome 式的日历化场景——那是一种刻意选择，而非「约定俗成的规范」。

永远的 0.x：1.0 恐惧症与谦虚文化

THESIS「觉得软件还不够格，不肯升高位」是一种真实、普遍、甚至有自己网站的工程文化——你的「谦虚表达」绝非孤例。

ZeroVer：一个专门为 0.x 而办的网站§5.1

0ver.org（2018 年由 Mahmoud Hashemi 发布，始于愚人节戏仿，内容却句句属实）收录「有 logo、有维基百科条目、却没有 1.0」的著名软件。其判定标准：

"If a project has a logo or Wikipedia article, but not a major version, it's officially 0ver." 有 logo 或维基条目却没有主版本号，即属 0ver。 — 0ver.org, About

它揭示的行业现实是：很多核心基础设施软件在 0.x 阶段就被生产环境大规模依赖——而 0.x 按 SemVer 意味着「任何东西都可能随时改变」。

长期 0.x 的荣誉成员§5.2

项目0.x 停留结局 / 现状
Terraform2014–2021，约 7 年期间已成 IaC 事实标准，2021 才「毕业」1.0
Node.js2009–2015，约 6 年与 io.js 合并后直接跳 4.0，跳过 1.0
Bitcoin Core2009–2021，12 年0.21.0 直接跳 22.0——第一个去掉前导 0 的版本，跳过 1.0
OpenSSL1998–2010，12 年0.9.8 系列发了十几年，2010 才 1.0.0
React Native2015–至今仍未 1.0，全球最广泛使用的 0.x 软件
Solidity至今 0.8.x整个 Web3 世界构建其上
Apache Kafka0.7→0.11，6 年期间已是 LinkedIn/Uber 生产核心，2017 才 1.0
MAME1997–至今，近 30 年「永远 0.x」阵营的旗帜，从未打算 1.0

Wine 的 15 年：1.0 恐惧症标本§5.3

Wine（让 Windows 程序跑在 Linux 上的兼容层）1993 年立项，2008 年 6 月 17 日才发布 1.0——历时 15 年。期间版本号长期在 0.9.x 徘徊，1.0 的发布被社区视为历史性事件。

为什么项目不肯发 1.0？因为 1.0 在文化上意味着：承诺向后兼容、接受维护责任、承认「可以被评判」。发 1.0 是心理上的签字画押。Rust 社区论坛对此有精准诊断——大量已被生产采用的 crate 永远停在 0.x，"root problem is Semver"：升到 1.0 意味着承诺未来每个版本都保持稳定，维护者因此不敢毕业。

反向操作：跳过 1.0 的「虚无主义」§5.4

另一类项目对 1.0 毫不在意甚至直接跳过：Bitcoin Core 0.21.0 → 22.0；Node 0.12 → 4.0；React 0.14.7 → 15.0.0。React 官方的解释值得全文引用：

"If major version numbers indicate API stability... then we got there a long time ago. There are too many preconceived notions of what v1.0 is. We're still following semver. We're just communicating stability by moving the 0 from the beginning to the end." 如果说主版本号代表 API 稳定，那我们早就到了——「v1.0」被赋予了太多先入为主的想象。我们仍然遵循 SemVer，只是把 0 从开头挪到了结尾。 — React 官方博客《New Versioning Scheme》, 2016-02
本章结论 · §5 SUMMARY

回答疑问 (d)：「自评不够好所以停在低位」是业界真实存在且广泛共鸣的心态——它有官方术语（ZeroVer / 0.x 文化）、有代表性项目（Wine / MAME / Terraform / React Native）、有心理学解释（1.0 = 承诺）。把它写成明文规则并一致执行，比「嘴上谦虚、手上乱升」专业得多。

时间即版本：CalVer 与滚动发布

THESISSemVer 之外的第二大规范是 CalVer（日历版本）——版本号直接编码发布时间；而其极端形态「滚动发布」干脆消灭了版本号。

CalVer：版本号 = 发布日历§6.1

calver.org 官方定义：「基于项目发布日历的版本约定，而非任意数字。」规范组件可自由组合：Major = 日历年（YYYY/YY/0Y）；Minor = 月（MM/0M）或周（WW/0W）；Micro = 该时段内第几次发布；Modifier = 可选后缀（-dev、-rc1）。常见完整方案：YYYY.MM.MICRO、YY.0M.MICRO。

采用者：Ubuntu、pip 与 JetBrains 全家桶§6.2

  • Ubuntu：YY.0M 格式——24.04 即 2024 年 4 月的 LTS。第一个版本就是 4.10（2004 年 10 月），从来没有 1.0。每 6 个月一版，每两年 4 月一个 LTS，LTS 提供 5 年标准维护。
  • pip：2018 年从 SemVer 切换到 YY.MINOR.MICRO——pip 的「破坏性变更」由弃用周期驱动，不由版本号信号驱动。
  • Twisted / Black：YY.MM.MICRO。CalVer 案例分析直言：「像操作系统一样，Twisted 有很多部件，各部分各自弃用与破坏兼容，SemVer 难以适配。」
  • PyCharm / IntelliJ 全家桶：2024.1、2025.2……年份 + 年内序号；NixOS：24.05、24.11……

Stripe：日期版本的教科书§6.3

Stripe API 把版本号做成工程艺术品：每次破坏性变更发布一个日期版本（如 2023-08-16）；账户首次调用时永久 pin 住当时版本，旧版本长期可用，升级是用户显式行为，可用 Stripe-Version 请求头逐请求覆盖。2024 年 9 月起升级为双层：每月发一个无破坏性的日期版本，每年两次发布命名主版本（acacia、dahlia……）承载破坏性变更——当前版本 2026-08-26.dahlia。

网站没有版本号§6.4

2009 年 Velocity 大会，Flickr 的 John Allspaw 与 Paul Hammond 发表《10+ Deploys Per Day》——每天向生产环境部署 10 次以上，这场演讲是 DevOps 运动的奠基文献之一。当用户每天无感知地收到十几次更新，「版本号」对网站用户失去意义；SaaS 对外的「版本」退化为 changelog（发生了什么）而非编号。Arch Linux 把这一哲学推到极致：纯滚动发布，「没有 'Arch 12' 这种东西，只有仓库的当前状态」，安装镜像的月度日期快照（2026.08.01）只是切片，不是版本。

但 API 必须有版本。网站自身可以不设版本，对外契约却必须显式版本化——因为客户端代码是别人写死的。Google AIP-185（官方 API 设计规范）规定：所有 API 必须提供主版本号，编码在 URI 路径第一段（/v1/...）；禁止暴露 minor/patch——「Google APIs use v1, not v1.0, v1.1, or v1.4.2」；主版本就地更新，旧版本关闭前必须经过充分公告的废弃期。

图 6.1 — 版本号的两大坐标轴：语义轴承诺兼容，时间轴承诺新鲜
本章结论 · §6 SUMMARY

版本号的两大坐标轴：语义轴（SemVer，承诺兼容性）与时间轴（CalVer，承诺新鲜度）。长期维护的发行版和 API 偏爱时间轴，因为「任意数字」扛不住十年尺度；库偏爱语义轴，因为依赖解析器需要兼容性信号。选择哪根轴，取决于谁在读你的版本号。

跳号：营销、避讳与对齐

THESIS版本号跳变在业界司空见惯，理由从营销震撼到代码避讳应有尽有——这再次证明版本号的本质是沟通工具，而非数学对象。

著名跳号案例§7.1

案例跳变真实原因
Java1.2 → 5 → 62004 年 J2SE 5.0 加了泛型/枚举/注解，市场团队认为「1.5 不够震撼」，marketing 名直接改 5.0（内部仍 1.5）；2006 年起彻底放弃 1.x
PHP~~6~~ → 7PHP 6 是真实存在过的开发项目（Unicode 字符串改造），烂尾放弃；为避免与已出版的《PHP 6》书籍混淆，2014 年社区投票定名 PHP 7
Windows8.1 → ~~9~~ → 10社区主流解释：大量遗留代码用 if (version.StartsWith("Windows 9")) 检测 Windows 95/98，叫 9 会误触发；同时「10」营销上更显跨代

营销名与工程号的割裂§7.2

Java 是典型：市场名（Java 5/6/7/8）与内部名（1.5/1.6/1.7/1.8）长期并行。Windows 更是三轨并行：营销名（Windows 11）、半年度功能更新名（24H2/25H2）、真正的技术版本 build 号（26100/26200/28000）。插曲：2015 年微软布道师 Jerry Nixon 宣称「Windows 10 将是最后一个版本」（Windows as a Service），2021 年 Windows 11 发布，成为著名「打脸」案例——营销性承诺随时让位于商业决策。

curl 8.0.0：because we freaking can§7.3

curl 作者 Daniel Stenberg 明确声明 curl 不用 SemVer：curl 承诺永不破坏 ABI/API，「主版本号永远没有理由涨」，于是版本号每次发布只 +0.01，7.x 持续了二十多年。curl 8.0.0 发布于 2023 年 3 月 20 日——curl 诞生 25 周年当天，8.0.0 是刻意安排的生日凑整，不代表任何破坏性变化。

"curl 8.0.0, because we freaking can." curl 8.0.0——因为我们就是想这么做。 — Daniel Stenberg 博客标题, 2023-03-20（curl 25 周年当天）

TeX 与 METAFONT：趋近 π 与 e 的渐近版本号§7.4

Donald Knuth 为他的两个作品设计了数学浪漫主义版本规则：TeX 版本号趋近 π（3 → 3.1 → 3.14 → …，当前 3.141592653，2021）；METAFONT 趋近 e（当前 2.71828182）。每修一个 bug，小数后再加一位。Knuth 明确规定：他去世后，软件冻结，剩余 bug 一律转为 feature（文档化），TeX 版本号定格为 π，METAFONT 定格为 e。

图 7.1 — Knuth 的渐近版本号：TeX 逼近 π，METAFONT 逼近 e（虚线为永远到不了的渐近线）

这是「版本号即无限序数」的极端案例：天然单调、天然有界。与「第三位无限 +1、永不进位」的规则在哲学上完全同构。

本章结论 · §7 SUMMARY

跳号案例的共同点是：版本号的目标受众从「依赖解析器」变成了「市场与货架」。数字承载品牌叙事（跨代感、整齐感、避讳、生日），兼容性承诺改由其他渠道（LTS 标签、支持矩阵、迁移指南）表达。

反对的声音：SemVer 批判与幽默规范

THESISSemVer 并非没有对手——理论上它有 Hyrum 定律这个「天敌」，实践上违规普遍存在，哲学上 Rich Hickey 说「这是个谎言」，幽默社区则干脆另立规范。

Hyrum's Law：SemVer 的理论天敌§8.1

Google 工程师 Hyrum Wright 提出、Titus Winters 命名的海勒姆定律：

"With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody." 一旦 API 的用户足够多，你在契约里承诺了什么并不重要——系统的一切可观察行为都会被某些人依赖。 — Hyrum's Law, hyrumslaw.com

推论（隐式接口定律）：「使用足够多时，不存在私有实现。」用户会依赖未文档化的怪癖、错误消息文本、时序与性能特征，形成 bug-for-bug compatibility。于是：SemVer 第 1 条假设「公共 API 可精确声明」，但 Hyrum 定律表明实际契约 = 一切可观察行为——「修复一个 bug」对依赖该 bug 的用户就是 breaking change。

实证：违规是常态§8.2

对 crates.io 下载量前 1000 的 crate、超过 14,000 个发布版本分析，结论触目惊心：

EMPIRICAL · 发布维度

约 1/31 的发布存在 SemVer 违规

且超过 1/6 的包至少违规过一次。研究者评论：「对维护者苛求完美是天真的……当勤奋、尽责、善意的人们犯错时，失败不在人，而在系统。」

EMPIRICAL · 生态维度

「SemVer 只是政策，无法强制，只能被自愿接受」

IEEE TSE 论文实证比较 Cargo、npm、Packagist、Rubygems 四大生态。Cargo 官方文档自己也留有余地：「这些只是指导方针而非铁律……通常靠维护者判断。」

Rich Hickey：「Spec-ulation」（2016）§8.3

Clojure 作者 Rich Hickey 在这场著名 keynote 中系统性抨击 SemVer：

"This is a lie. This cascading version bumping happens all the time." 这是个谎言。级联式版本递增无时无刻不在发生。 — Rich Hickey, "Spec-ulation", 2016

他的替代主张：软件演进只有三种合法操作——accretion（只增不改）、relaxation（放宽要求）、fixation（固化）；绝不应在原地做破坏性变更——「如果你要破坏它，就给它起个新名字」。他还调侃 SemVer 规范自身也在改版：「when you start versioning your versioning...」（当你开始给你的版本规范做版本控制……）。

语言社区的两种极端答案§8.4

CASE · GO

永远不出 Go 2

2012 年 Go 1 发布时给出兼容性承诺：为 Go 1 编写的程序将在所有 Go 1.x 下继续正确编译运行。社区呼唤 Go 2 多年，Russ Cox 2023 年定调：永远不会有一个破坏 Go 1 程序的 Go 2；破坏性演进通过 GODEBUG 与 go.mod 按模块粒度消化。

CASE · PYTHON

2→3 的十年之痛

Python 3.0（2008）是有意的不兼容发布；2.7 的 EOL 从 2015 被迫延至 2020，整个迁移耗费社区十年以上——「主版本号破坏性变更代价」的教科书案例。官方明确表示不会再有 Python 4 式断裂。

幽默规范：版本号的诗意一派§8.5

SENTIMENTAL VERSIONING

「有时我们真正想要的是一首诗」

sentimentalversioning.org（Dominic Tarr，2014），副标题 "Version One dot Okay"，许可证一栏写着 "Artistic License, of course"。名言："Sometimes a version is just a number, but sometimes what we really want is a poem." 唯一硬性要求：版本号必须对作者本人有意义。

PRIDE VERSIONING · PROUD.DEFAULT.SHAME

骄傲、平庸与羞耻

pridever.org（Niki Tonsky）：为真正骄傲的改动 +PROUD（后两位清零）；平庸的常规发布 +DEFAULT；修复羞于启齿的 bug +SHAME。另见 ZeroVer（0ver.org）：你的主版本号永远不应超过计算机科学中最重要的数字——0。

版本号是一面镜子§8.6

态度代表版本号哲学
完美主义焦虑Wine（15 年）、MAME（永远 0.x）「还不够格」
承诺型Go（v1 兼容性承诺）、curl（永不破坏 ABI）「数字即契约」
日历型Chrome / Firefox / Node / systemd「数字即时间」
虚无/跳号型Bitcoin Core、PHP、Windows「数字不携带语义」
诗意型TeX（π）、Sentimental / Pride Versioning「数字即表达」
批判型Rich Hickey、"SemVer is a lie"「任何兼容承诺都是幻觉」
本章结论 · §8 SUMMARY

六种态度照出同一个事实：版本号是项目心态的镜子，而不是客观的兼容度量。认清这一点后，「选哪种规则」的重要性让位于「把规则写下来并一致执行」。

双轨制：给机器一个号，给人类一个名

THESIS两大移动平台官方强制的「双轨制」——内部单调号给机器排序，外部字符串给人类阅读——是所有版本实践的母版。

Android：versionCode 与 versionName§9.1

Android 官方文档《对应用进行版本控制》明确规定：versionCode 是正整数，内部版本号——「此数字有助于确定某个版本是否比另一个版本更新……这不是向用户显示的版本号。」每次发布接续版本时必须递增；Google Play 允许的最大值为 2100000000。低 versionCode 的 APK 无法覆盖安装高 versionCode 的应用。versionName 则是向用户显示的版本号，自由字符串，官方建议用语义化版本，仅作展示。

iOS：CFBundleShortVersionString 与 CFBundleVersion§9.2

iOS 同样双轨：CFBundleShortVersionString（Xcode 里的 Version）是 user-visible 发布版本号，强制格式 Major.Minor.Patch 三段整数，可本地化；CFBundleVersion（Xcode 里的 Build）是构建迭代号（含未发布构建），不可本地化，前导零被忽略；同一 ShortVersion 下可上传多个 Build。

Windows 的三轨§9.3

营销名（Windows 11）＋ 半年度功能更新名（24H2/25H2/26H1）＋ build 号（22000 → 26100 → 26200 → 28000）；Windows 10/11 的内核版本号至今都是 NT 10.0。

macOS 10.16：一次跳变背后的兼容妥协§9.4

Big Sur 跳 11.0 时，为兼容写死检查「10.x」字符串的旧软件，通过 SYSTEM_VERSION_COMPAT 机制对旧 SDK 编译的程序与浏览器 UA 自报 10.16——主版本跳变时，对机器世界撒一个向后兼容的「谎」。

综合全部案例，版本号实际承担四种职能，且常被拆给不同字段：

职能回答的问题载体实例

结论：玄览的版本规则在业界坐标系中

THESIS玄览现行规则（versionName 第三位无限 +1 不进位；第一、二位仅按明确指令调整；versionCode 单调 +1）在业界坐标系中完全成立，且有高贵的先例血统。

回答四个原始问题§10.1

QUESTION (a)

AI 每次更新都升大版本号，符合惯例吗？

不符合。那是把 SemVer（为「有公共 API 的库」设计的规范）机械套用到独立应用上。业界对应用的主流做法是二选一：日历化（Chrome/Angular/Node，主版本号 = 节奏）或冻结高位（微信/macOS/Minecraft/Office，低位承载日常迭代）。「每次必升大版本」不属于任何一派。

QUESTION (b)

「1.x 或 2.1.1000 多」的那个数字叫什么？

第三位，官方名称 patch（SemVer）或 micro（Python/CalVer）。观察到的形态 = 冻结第一、二位，第三位无限递增。

QUESTION (c)

每次更新非要动第一位和第二位，是不是有问题？

是。第一、二位在文化上是「叙事权」——动它们等于宣布「这次不一样」。频繁动高位会让版本号丧失信号价值（通胀），或者虚假承诺里程碑（虚张声势）。Linux 内核、微信、macOS 的实践一致表明：高位不动是常态，动是例外。

QUESTION (d)

只在最后一位更新，作为谦虚表达成立吗？

完全成立。它有官方术语（ZeroVer / 0.x 文化）、有最高贵的先例（Knuth 的 TeX 渐近 π：「每修一个 bug，小数后再加一位」）、有工业界最大规模验证（Linux 2.6.x 八年、微信 8.0.x 五年、Office 16.0 十一年、MAME 近三十年）。谦虚不是版本号的缺陷，而是一种有传承的工程姿态。

玄览规则的对照表§10.2

两点补强建议§10.3

  • 第三位改名 micro 更贴切玄览的第三位不做「仅 bug 修复」的语义承诺，叫 patch 名不副实；Python/CalVer 体系的官方术语 micro（微版本号）更准确地描述「第 N 次发布」这一职能。
  • 谦虚之外，补一句「毕业条件」业界共识（SemVer FAQ）认为「上生产、有稳定契约、开始担心兼容性」就是该毕业的信号。建议在 VERSIONING.md 中写明：当玄览自觉达到这三个信号时，第一、二位的调整通道是敞开的——这使规则从「永远谦虚」升级为「谦虚但诚实」。

一句话总纲§10.4

FINAL THESIS · 总纲
版本号的本质不是数学，而是沟通：
规则本身没有对错，可预期、可文档化、被一致执行，
才是版本号真正的「语义」。
